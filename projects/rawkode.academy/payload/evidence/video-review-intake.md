# Bounded review intake contract

This slice supplies the staff API, streaming quarantine upload, and trusted deliverable contract. It does not install a Container/FFmpeg or Workers AI provider, add an upload UI, deploy, migrate remote databases, or alter the public watch page. `configuredMediaAdapter()` returns undefined: a successfully uploaded source remains private and `process` returns 503. Synthetic fixture review remains available only under its existing explicit loopback gate.

The later [durable processing boundary](video-review-processing.md) supersedes the shared one-hour processing deadline and completion-order attachment described below. It adds a persisted 24-hour job deadline and expected-current guard; the configured provider remains unavailable.

## Staff API

All requests use the existing authenticated Payload/OIDC staff identity. POST and PUT require the exact configured Origin, including through the preview bridge. Session ownership and video access are checked before reading upload bytes. JSON commands are capped at 256 KiB.

1. `POST /api/review/uploads` with `{action:"begin", commandId:<UUID>, videoId, bytes, checksum:<lowercase SHA-256>, contentType, metadata}`. Supported source assertions are video/mp4, video/quicktime and video/webm. The server chooses independent session, revision-command and R2 object keys. Replaying the same command and owner returns the original session; changed input or owner returns 409. Persist the command ID before the first request.
2. PUT the bytes to the returned `uploadUrl`, with matching Content-Type and Content-Length. Maximum 64 MiB; no multipart/resume support. A native FixedLengthStream enforces actual length and R2 validates SHA-256 while streaming. Quarantine metadata is application/octet-stream. Client MIME is only an assertion for the later trusted probe. A retry verifies the existing object, never overwrites it; R2 success followed by a failed D1 write is recoverable.
3. `GET /api/review/uploads?sessionId=<UUID>` returns owner-only status, expiry and processing availability, without raw R2 keys.
4. `POST` `{action:"process",sessionId}` dispatches/polls an installed durable adapter. The adapter must return promptly with `{state:"processing"}` until its Workflow/Container job completes. Its job ID and immutable recipe must remain stable across retries; HTTP requests must not own encoding lifetime. No browser attestation endpoint exists.
5. `POST` `{action:"cancel",sessionId}` fences pending/uploaded/processing registration. Ready assets are retained. Retrying cancellation is safe.

The one-hour session deadline currently covers both uploading and processing/finalization. Jobs completing after it cannot register assets. A ready session can retry its idempotent revision attachment after expiry. A future provider must cancel/stop jobs at this deadline; extending processing lifetime requires a separate persisted deadline design, not silently ignoring expiry. Successful first attachment becomes the current revision in completion order; a delayed session may supersede a newer cut. Prior approval/publication remains intact. Before provider activation, confirm this staff workflow or introduce an expected-current attachment guard.

## Trust and persistence

`ContainerMediaAdapter` owns actual stream inspection, full decode and H.264/AAC fast-start MP4 encoding. Attestation binds source key/ETag/SHA/size, job, immutable recipe SHA, output key/ETag/SHA/size, duration, codecs and dimensions. Schema validation and R2 HEAD checks reject wrong source, video, output, MIME assertion, digest, size, recipe or job. The server never treats upload MIME, caller duration or caller JSON as proof of playable media. `WorkersAITranscriptionAdapter` is a separate future interface; generated transcript text never establishes approval or playability.

A guarded D1 batch registers both media records, immutable source/deliverable associations and the complete attestation. Cancellation or a competing result invalidates the batch. Identical concurrent attestations reuse the same assets. Revision creation uses the persisted command ID, so a failure between asset registration and revision creation is recoverable. Source/output pairing prevents cross-session or cross-video substitution. Intake tables are deliberately internal and unavailable through Payload collection mutations. Future migrations must retain these tables and triggers; downgrade refuses any session history.

Private playback checks stored SHA-256/ETag/size, then streams conditional range reads. Publication reuses the attested immutable output object and stores its exact key/ETag/SHA/size; it makes no whole-object copy. Public playback continues to check the publication's ETag/size and conditional read. Existing fixture staging/rehashing is unchanged. The original source stays private.

There is intentionally no object deletion on retries or cancellation: racing workers must not delete a winning or published object. Failed, cancelled and expired uploads may retain private objects and incur storage cost. Cleanup is not implemented or scheduled. Before provider activation, add a job-aware reaper: fence expired/cancelled sessions, confirm the durable job has terminated, wait a grace period, recheck that neither key appears in immutable assets/publication events, then conditionally delete only the session-owned keys. Never attach a blanket lifecycle rule to the shared intake prefix because successful deliverables remain there for publication. Large/resumable uploads and per-user storage quotas remain outside this bounded slice.
